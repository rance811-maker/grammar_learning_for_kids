# PRD Coach｜把"我想要个啥"追问成机器能执行的需求

## 为什么需要这一步

AI 不会拒绝一个烂需求。它会非常认真、非常快地，把烂需求实现出来。

0-1 阶段最贵的浪费，就是拿着没想清楚的需求直接开工——烧掉时间和 token，你还以为自己在前进。

这个 skill 的职责：**在写第一行代码之前，把需求逼到可执行。**

## 铁律

1. **一次只问 1–2 个问题。** 一次抛十几个问题，用户只会敷衍作答，你收集到的是噪音。
2. **不接受抽象答案。** "提升效率""体验更好""更智能"一律追问到**具体、可观测、可证伪**。
3. **必须问满四组。** 后三组是新手几乎必漏的，其中「拿什么做」和「怎么算对」最致命。缺了任何一组，PRD 不算完成。
4. **允许用户说"不知道"。** 他不知道时，给 2–3 个具体选项让他选，而不是继续追问抽象问题。
5. **发现做不成要直说。** 两种情况必须当场讲明白，不要顺着往下做：
   - 痛点不成立，或已有成熟方案能解决 → 这是伪需求
   - **关键数据拿不到** → 这个想法当前做不成，给出替代路径（换数据源 / 缩小范围 / 先用人工跑通）
6. **不要在追问过程中写代码。** 这个 skill 只负责把需求问清楚并产出 PRD。

## 追问协议

### 第一组 · 要什么

**Q1 谁在什么场景下用？他现在是怎么凑合的？**
- 追问到具体的人、具体的时刻
- ❌ "给所有想学英语的人" → 追问："具体是谁？多大？一天里什么时候会打开它？"
- "现在怎么凑合的"尤其重要：没有替代方案的需求，往往是伪需求

**Q2 要解决的那个"痛"是什么？（一句话，且可证伪）**
- 判据：这句话能不能被事实推翻？不能被推翻的就不是需求，是口号
- ❌ "学习效率低" → 追问："低到什么程度？你是怎么知道的？"

**Q3 做完之后，什么变了？（可观测的成功标准）**
- 必须落到能被观察或测量的变化上
- ❌ "家长更省心" → 追问："省心体现在哪个看得见的行为上？"

### 第二组 · 拿什么做　← 最容易直接否掉一个想法

很多想法失败，不是因为需求不清楚，是因为**它依赖的东西根本拿不到**。

AI 让"实现"变便宜了，瓶颈就前移到了"你手上有没有原料"——**模型再强，也变不出你没有的数据**。

**Q4 这东西要跑起来，需要哪些数据或内容？**
- 要具体列出来
- ❌ "用户数据" → 追问："具体是哪几项？举一条真实的例子。"

**Q5 它们现在在哪？你拿得到吗？**
- 逐项确认落在哪一类：
  - 在你手上（文件、表格、笔记）
  - 在别人手上（需要协调）
  - 在某个你没权限的系统里
  - **根本不存在，得从头攒**
- 只要有一项落在后两类，就当场说明白：这决定了它是"今天能做"还是"三个月后才能做"

**Q6 是用户自己填、你预先备好、还是从别的地方接进来？**
- 这三个答案会做出**三个完全不同的产品**，必须现在就定
- 用户自己填 → 他愿不愿意填？填错了怎么办？
- 你预先备好 → 谁来维护？多久会过期？
- 从别处接 → 有没有接口？有没有权限？稳不稳定？

### 第三组 · 不要什么

**Q7 这一版明确不做什么？**
- **强制用户至少列出 3 条**
- 这既是防止 AI 自由发挥，也是防止范围蔓延的关键
- 如果用户列不出来，说明范围还没想清楚，回到 Q2

**Q8 有哪些硬约束？**
- 成本 / 时间 / 技术栈 / 合规 / 平台
- 一定要问一句："有没有绝对不能碰的东西？"

### 第四组 · 怎么算对　← 几乎全漏，但对 AI 最关键

**Q9 给一个正例：什么样的结果算做对了？**
- 具体到能直接拿来验收，最好是一段真实的「输入 → 期望输出」

**Q10 给一个反例：什么结果看起来像做完了，其实是错的？**
- **这一条价值最高。** 它把用户脑子里"不言自明"的标准逼出来
- 示例："生成了 10 道题，看着挺像回事，但其中 3 道题的标准答案本身是错的"
- 它同时是后续迭代的地基——**没定义什么算对，就无从判断一次改动是变好还是变坏**

## 收敛判据

四组问题都有具体答案，且全部满足才能进入输出：

- [ ] 痛点是一句可证伪的话
- [ ] 成功标准可观测
- [ ] **所需数据逐项确认过来源，且确认拿得到**
- [ ] 至少 3 条"明确不做"
- [ ] 正例、反例各至少 1 个

**未满足则继续追问，不要提前进入输出。**

> 如果是**根本做不出来**，多半卡在「拿什么做」那张表。
